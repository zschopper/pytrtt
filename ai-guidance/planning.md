# Project Planning

- When present, use private `work/docs/project_hu.md` as the sole local project plan; locate relevant headings first.
  It is excluded from Git. In a fresh clone, use README, maintained artifacts, and the task context;
  do not require private files or invent missing decisions.
- Read the current state, related accepted decisions, and next tasks before proposing work; preserve settled decisions.
- Distinguish user requirements, accepted decisions, proposals, implementation, and verified results.
- Give each next task a concrete output, dependencies, and a verification criterion. Resolve routine choices autonomously;
  ask only for missing product decisions or information that materially changes scope.
- New game/build/DLC support requires separate evidence; shared archive versions do not prove shared text formats.
- Keep extraction, translation, binary writing, restoration, and in-game appearance as separate verification results.
  Source inspection, unit tests, and dry runs do not establish in-game success.
- Link technical findings to files or exact reference commits. Record commands, artifact paths, and checks actually run;
  label planned or unrun checks. Do not infer unsupported games from incomplete downloads.
- Update superseded text when the user clarifies a requirement. Keep decided and open questions at the plan's end;
  implementation backlog is not an unanswered product decision.
- For a translation project, use `translation/project-workflow.md`; for historical evidence, use `references.md`.
